# 翻译腔套路库：怎么改（第二段的查表）

本文件承接 SKILL.md 的"第二段：决定怎么改"。判断某处要动之后，
从这里查套路、查对照表。原则：**准确比有力量感更重要**。
自然中文往往不依赖物理隐喻来说清抽象概念。

## 套路一：用物理动作描述思考过程

用描述物理动作的动词来比喻思维活动。这些词看起来有力量，
但在中文日常表达中没有对应搭配。

| 常见问题词 | 中文自然说法 |
|------------|-------------|
| 接住（反馈/观点） | 收到、记下、同意 |
| 击穿（论证/逻辑） | 不成立、站不住脚、失效 |
| 锋利（重构/论点） | 准确、到位、精炼 |
| 拆解（问题/框架） | 分析、梳理、分开看 |
| 收口（结论/讨论） | 总结、归纳、收尾 |
| 不崩 / 不爆 | 不乱、不出问题、稳定 |
| 撑不住 | 不行、不够、维持不了 |
| 打穿 / 穿透 | 深入、触及、覆盖 |
| 收紧 / 收窄 | 缩小、聚焦、限定 |
| 落地 | 实施、上线、做成 |
| 扛住 | 承受、支持、管够 |
| 推开（思路/边界） | 延伸、扩展、展开说 |
| 承担（逻辑责任） | 负责、承受 |

此表不是死规则：如果原文语境里该物理动词确实是作者自己的用法
（比如口语里真有人这么说），按 SKILL.md 第一段"毛边先假设是手迹"处理。

## 套路二：用形容词替读者先下判断（X很Y：起手式）

段落或句首出现「形容词 + 冒号」结构，在读者看到具体内容前
就替他们做了评价。

**典型模式：**
- 逻辑很清晰：
- 问题很直接：
- 结论很明确：
- 原因很简单：
- 更锋利：
- 更干净：

**修复方法：** 直接把形容词那一节删掉，只留冒号后面的事实。
如果特别想保留形容词，说明后面内容没讲清楚，应该回头补充事实，
让事实本身说服读者。

## 套路三：用抽象名词做主语，用形容词当结论

句式骨架：「X 的 Y 比 Z 更 W」

**典型模式：**
- 工程上的现实比这些数字更难看
- 理论上的可能性比实践更复杂
- 技术上的挑战比预期更严峻

**三个问题：**
1. 「工程上的现实」「理论上的可能性」等抽象名词堆叠做主语，不够具体
2. 「难看」「复杂」「严峻」等评价性形容词做结论，读者不知道具体哪有问题
3. 整个句式是英文骨架的直接翻译

**修复原则：** 让人、动作或具体对象做主语，让事实自己说话。
把评价词换成具体描述。

## 套路四：有中文译法的英文词直接混入句子

英文术语有现成稳定中文译法却未翻译，直接保留原文。

**常见应翻译的术语（已有稳定中文译法）：**
- context → 上下文
- state → 状态
- cache → 缓存
- claim → 断言
- runtime → 运行时
- protocol layer → 协议层
- contract layer → 契约层
- interface → 接口
- implementation → 实现

**保留英文的情况（中文技术圈尚未统一术语）：**
- prompt（提示词/指令/提示，仍在竞争中）
- embedding（嵌入/向量化，仍在竞争中）
- tokenizer（分词器/标记器，未完全统一）
- agent（智能体/代理，仍在竞争中）
- harness（运行时/框架/客户端/载体，还在竞争中）

**修复原则：** 除非该英文词在中文里没有稳定译法，否则全部换成中文。
